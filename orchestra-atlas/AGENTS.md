# Orchestra Atlas — AI 專案開發手冊 (`AGENTS.md`)

> 本文件是本專案的權威開發規範。任何 AI Agent 在新增、修改、重構或修正專案前，應先閱讀本文件，再閱讀 `README.md` 與相關程式碼。

## 1. 專案目的與成果定義

Orchestra Atlas 是一個以繁體中文為主、兼具英文術語的「互動式管弦樂配器知識庫」。對象是音樂學習者、編曲者與對管弦樂好奇的讀者。核心目標是：讓新增一種樂器或一篇配器技巧時，可以直接增加一筆結構化資料，無須重複撰寫卡片、詳情視窗或篩選程式。

**每次內容更新應交付：** 變更後的 `content/entries.json`、必要時才修改的前端檔案，以及通過 `python3 scripts/validate.py` 的驗證結果。

**完成標準：** (1) 資料驗證通過；(2) 首頁可載入；(3) 搜尋、分類篩選與詳情視窗正常運作；(4) 手機寬度下沒有橫向溢出；(5) 原本條目與連結未遭破壞。

## 2. 技術限制

- 使用原生 HTML / CSS / JavaScript，不使用 React、Node build、後端、資料庫或需設定 API key 的服務。
- GitHub Pages 可直接部署；所有站內資源使用相對路徑，避免寫死 repo 名稱或根目錄 `/`。
- `content/entries.json` 是內容的**唯一事實來源（single source of truth）**。卡片與詳情內容不得另行硬編碼在 HTML。
- 網站以繁體中文為主，音樂英文術語作補充。不得虛構引用或把未經核實的演奏限制寫成絕對事實。
- 不加入受版權保護的樂譜、錄音、圖片或影片，除非已取得授權或確認符合可使用條件。
- 不需外部圖片即可完整閱讀內容。Google Fonts 為非必要字型，離線時採系統字型。

## 3. 檔案與目錄結構

```text
orchestra-atlas/
├── AGENTS.md               # AI 遵循的標準作業規則
├── README.md               # 人類閱讀的專案簡介、操作方式、發布教學
├── index.html              # 唯一入口，首頁與語意化結構
├── assets/
│   ├── style.css           # 全站設計系統與 RWD
│   └── app.js              # 資料載入、搜尋、篩選、詳情功能
├── content/
│   └── entries.json        # 所有樂器與技巧內容
├── scripts/
│   └── validate.py         # 內容 schema 與關聯驗證
└── examples/
    └── new-entry-example.json  # 新增內容的範例（不會被網站載入）
```

檔名一律小寫；資料 ID 使用英文 kebab-case（例如 `oboe`、`string-divisi`）。若未來新增圖片，放在 `assets/images/<entry-id>.<ext>`，必須提供替代文字，並避免使用中文、空白或特殊符號作檔名。

## 4. 視覺與介面規範

- 風格：深藍綠基底、低彩度的薄荷綠與暖金色點綴；典雅、清楚、克制，避免浮誇漸層和多餘動畫。
- 全站顏色、字級及留白盡可能由 `assets/style.css` 集中管理；不要在新增內容時私自製作不同版型。
- 一筆條目對應一張卡片，點擊後在同一個 `<dialog>` 開啟詳情。不為每筆新資料複製一個 HTML 頁面。
- 響應式設計：桌面三欄、平板兩欄、手機一欄；所有互動元件要有可辨識的文字及鍵盤操作方式。
- 保留既有導覽、搜尋、分類、統計數字、相關條目連結。若需要變更整體資訊架構，先說明原因與影響範圍。

## 5. 資料格式（必填 schema）

`content/entries.json` 最外層為 JSON array，每筆 object **恰好**包含以下欄位（不得任意更名、刪除或添加）：

| 欄位 | 類型 | 規則 |
|---|---|---|
| `id` | string | 唯一、小寫英文 kebab-case，建立後勿隨意修改 |
| `type` | string | `instrument` 或 `technique` |
| `category` | string | `strings`、`woodwinds`、`brass`、`orchestration` |
| `title` | string | 繁體中文名稱，非空白 |
| `english` | string | 對應英文名稱，非空白 |
| `subtitle` | string | 一句精簡、易理解的概述 |
| `tags` | string[] | 至少一個搜尋標籤 |
| `range` | string | 樂器的「概略音域」或技巧的「基本原則」，需標示適用範圍 |
| `character` | string | 音色特色或技巧核心概念 |
| `use` | string | 實際配器應用與具體情境 |
| `tip` | string | 一則實務提醒，避免無根據的絕對化說法 |
| `related` | string[] | 其他已存在的 `id`，可為空陣列，不得指向自己 |
| `icon` | string | 短符號或字元；不依賴外部圖庫 |

`type=technique` 必須搭配 `category=orchestration`；其他三種樂器分類搭配 `type=instrument`。現階段若需增加打擊樂、鍵盤等新分類，**必須同步修改**驗證腳本、前端的分類標籤與篩選按鈕，並重新檢查既有資料。不要只新增一個沒有對應 UI 的分類值。

## 6. AI 新增內容標準流程

1. **先讀規範：** 閱讀 `AGENTS.md`、`README.md`、`content/entries.json` 和 `scripts/validate.py`。
2. **決定內容類型：** 確認是樂器還是配器技巧，選擇既有分類，檢查是否已有同名或近義條目。
3. **撰寫可靠內容：** 以繁體中文精簡解釋，優先提供可理解的音色特色、具體使用方式、演奏限制。對音域、移調、最大同時發聲數等容易誤解的資訊，應使用「一般而言／依樂器、樂手、奏法而異」等合理限定；無法核實的數據不要杜撰。
4. **建立資料：** 依 `examples/new-entry-example.json` 與 schema 加入一筆 JSON object；保留已有 ID 及資料。不要直接手動加卡片 HTML。
5. **加入關聯：** 若 `related` 指向其他條目，必須確定目標 ID 已存在；必要時可以補上既有條目的反向關聯，但不可大量更改無關內容。
6. **執行驗證：** 執行 `python3 scripts/validate.py`；未通過前不得宣稱任務完成。
7. **手動驗收：** 本機透過 `python3 -m http.server 8000` 開啟網站，檢查卡片、搜尋、分類、詳情、相關條目跳轉與手機排版。
8. **回報：** 條列新增/修改的檔案、條目 ID、驗證結果，並說明任何尚未完成或無法確認的部分。

## 7. AI 修改程式的約束

- 最小變更原則：只更改完成任務所需的檔案；避免整頁重寫、批次改名或額外引入套件。
- 對既有內容進行事實修訂時，明確說明修訂原因；不要默默把原作者的個人意見改寫成宣稱客觀的事實。
- 新增互動功能必須同時考慮鍵盤、焦點、空結果、載入失敗與窄螢幕。
- 不可將 API key、個人資料、登入憑證上傳 GitHub。不得新增未經同意的第三方追蹤碼。
- 若使用者要求破壞性操作（刪除大量資料、重寫站點、改變資料格式），先提出影響摘要與備份方案，取得明確同意後再執行。

## 8. 驗收清單（每次更新都要跑）

- [ ] `python3 scripts/validate.py` 顯示 PASS。
- [ ] 新內容可被首頁自動載入並計入統計。
- [ ] 分類篩選可找到新條目。
- [ ] 搜尋中文與英文關鍵字都能找到新條目。
- [ ] 點擊卡片能打開完整內容，Esc 可以關閉。
- [ ] `related` 不存在壞連結，沒有 console error。
- [ ] 手機畫面正常，原本六個示範條目仍可閱讀。
- [ ] README 或相關文件在工作方式改變時同步更新。

## 9. 交辦示範（供下次使用）

> 請先閱讀根目錄 `AGENTS.md`，再依照規範新增一筆「雙簧管（Oboe）」條目。請說明音色、概略音域、適用的配器情境與限制，與長笛建立相關連結。不要修改整體版型；完成後執行 `python3 scripts/validate.py`，並回報修改的檔案與驗證結果。

這個交辦方式將「預期成品、修改限制、完成標準」三者寫清楚，因此可以跨對話或交給不同 AI Agent 重複執行。
